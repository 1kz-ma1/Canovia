# Canovia V35：V34移行後の安定性・PWA改善

対象：`1kz-ma1/Canovia`、V34マージ後の `f93d8fbda64a8d5446830adfdd2fa7580df7463c`。
ローカル作業コピーだけを変更しました。push・PR作成・本番デプロイ・本番DB操作は行っていません。新規Migration・依存パッケージの更新はありません。

## 優先順位と実装結果

|優先度|発見事項・影響|今回の対応|
|---|---|---|
|P0|V34のNginxが `/app.webmanifest` に存在しない静的ファイルを要求し、404になる。PWAのインストールとアカウント引き継ぎに影響する。|Laravelの既存動的マニフェストへ渡すよう修正。個別の引き継ぎURL・非キャッシュ指定を維持。|
|P0|rootで生成したstorage・キャッシュを、www-dataのFPMワーカーが書き換えられず500になる可能性。|起動時のキャッシュ生成後に、storageとbootstrap/cacheの所有者を修正。|
|P1|オフライン同期が、計画の権限確認より前に既存の同期IDを照合・返却していた。|先に編集権限を検証。既存IDは同じタスク・同じactorだけ再利用可。異なるactorやタスクは409。|
|P1|同じ同期IDの並行送信は「検索→作成」の間で競合する。イベント保存だけがトランザクション外。|既存の一意制約とLaravelのcreateOrFirstを使用。セッション・作業ログ・イベントを同一トランザクションで保存。|
|P1|同期失敗後のボタンが、ended_atを理由に処理を拒否し再試行できない。再表示でも終了済みカードが出ない。|「同期を再試行」を追加。終了時刻・作業時間・UUIDを保ったまま再送。再読み込み後も未同期カード・導線を表示。|
|P1|JSONを期待する同期リクエストでも、例外処理がapi/*以外にHTMLを返す。|Acceptヘッダーに基づくLaravel標準のJSON判定も尊重。通常のHTMLフォームは従来どおり。|
|P1|端末保存に失敗しても終了処理が進み、通信が終わらない場合はボタンが戻らない。|終了記録を保存できなければ送信しない。保存失敗を表示。同期通信は15秒で打ち切り、再試行可能にする。|
|P2|共同計画一覧でロード済みの会員情報を使わず、権限判定を繰り返すたびにDBを読む。|会員情報を一括取得し、読み込み済みの場合は追加問い合わせなしでowner/editor/viewerを判定。|
|P2|オフライン画面の3秒間隔の確認が、遅い通信時に重複。古いCSRF情報での同期も発生しうる。|確認処理は1本に制限し10秒で打ち切る。明示的オフライン時は送らない。保存済み作業を残し、オンライン画面の新しいCSRFで同期する。|
|P2|IndexedDBの接続を閉じずに残していた。|読み書き後にcloseし、versionchangeでも接続を閉じる。既存DB名・キーは維持。|
|P2|存在しないbuildファイルにも1年間のimmutableヘッダーが付く。|404には長期キャッシュ指定を付けない。実在するハッシュ付き資産の長期キャッシュは維持。|
|P2|V34起動は10000固定、FPMと終了処理はデフォルト頼み。ローカル生成物がDockerへ混入する余地もある。|PORT検証・反映、起動前構文確認、FPM最大4ワーカー/ondemand/500リクエストで再生成、QUITでの終了、public/hot・生成済み設定キャッシュの除外。|

P0はデプロイ・主要機能を妨げる項目、P1は記録・権限・復旧に関する項目、P2は性能と運用の改善です。負荷試験で速度向上率を測定したものではありません。

## 維持した仕様

- フィードバックの分類・評価・投稿・管理・更新情報との連携を維持。公開/非公開・公開取り消しの挙動をテスト。
- 未来メモのGuest所有、アカウントへの引き継ぎ、AI共有OFFの除外をテスト。内容・分類・プロンプト仕様は変更なし。
- 共同計画のowner/editor/viewerを維持。viewerによる作業同期は禁止、editorは利用可。
- オフライン中はタイマーの再生・一時停止、接続後に終了・記録する仕様を維持。保存形式・UUIDを維持。
- PaceKeeper時代の所有Cookie、IndexedDB名、actor識別、起動クエリ、互換ヘッダーを維持。
- Canoviaブランドへのホスト移行と一度限りの引き継ぎリダイレクトをテスト。
- Service Workerのシェル版のみv35へ更新。テーマはV33のダーク固定を維持。
- 更新情報の既存データ・表示・未読キーは変更なし。本ZIPには新しいリリース告知は追加していません。

## 検証結果

- 追加PHP回帰テスト：13件成功。
- JavaScriptの操作ロジックテスト：4件成功。失敗後の再試行、再読み込み後の再試行、端末保存失敗、起動確認の重複抑制。
- 全PHPテスト：73件中60件成功、10件失敗・3件エラー。V34原本も60件中47件成功で、同じ13件が失敗。今回増えた失敗はありません。
- `npm run build` 成功。lockファイル変更なし。
- Laravelのconfig/route/viewキャッシュ生成成功。検証用キャッシュは消去済み。
- LinuxのNginx 1.28.3実機で構文・HTTPテスト成功。動的マニフェストのFastCGI転送と元のURI・クエリ、healthの204/両互換ヘッダー、資産キャッシュ、404、sw.js、任意PHP/.env拒否を確認。

Nginx検証ではログ・公開ディレクトリ・ポート・ユーザーを検証用に置き換え、FastCGI応答はモックを使いました。Laravel処理は別途PHPテストで確認しています。Docker Desktopが応答せず、Dockerイメージ全体のビルド、PHP-FPM実起動、Supervisorと組み合わせた停止試験は未完了です。iOSホーム画面の実機動作、Aiven MySQL上の並行送信、40人同時負荷も未検証です。

### V34から残る既存テストの問題

13件の内訳は、旧画面文言/ブランドの期待値6件、旧設定キーを参照するフィードバック版数2件、管理認証設定1件、SQLiteの日付保存形式による日次状態の再保存失敗1件、テストデータのpublic_slug不足2件、DB準備のない単体テスト1件です。詳細なテスト名はZIPの `review/test-results.json` に収録しました。

SQLiteの日付問題は単なる文言差ではありません。本番MySQLで同じ不具合が起きるとは確認できていません。既存テストを緑にするためだけに、日次状態の本番保存仕様を変更することは避けました。

## ZIPの適用方法

ZIP内は次の構成です。

- `patch/`：追加・上書きするリポジトリ相対パスのファイル。
- `review/changes.diff`：追加ファイルも含むレビュー用差分。
- `review/manifest.json`：基準コミット、ファイルごとの適用前後SHA-256。
- `review/Check-Baseline.ps1`：指定したリポジトリの適用前ファイルを読み取り確認するスクリプト。
- `review/test-results.json`：変更前後のテスト件数と失敗テスト一覧。
- `rollback/`：今回変更する既存ファイルのV34原本。追加ファイルは含まない。

1. 手元のリポジトリがV34マージ後の状態で、未保存の変更がないことを確認。
2. 必要なら展開したZIPで次を実行して、上書き対象が基準と一致するか確認。

   ```powershell
   & .\review\Check-Baseline.ps1 -Repository '手元のCanoviaフォルダ'
   ```

   LF/CRLFの違いもハッシュ差として報告します。差があれば、そのファイルの差分を確認してから適用してください。

3. `patch/` の**中身**を、フォルダ構造を維持してCanoviaルートへコピー。`.dockerignore` も含める。`review/` と `rollback/` は上書きしない。
4. 差分を確認し、手元で `npm run build`、`php artisan test`、`node --test tests/js/offline-reliability.test.mjs` を実行。上記の既存失敗を区別する。
5. Docker環境では `docker build -t canovia-v35-check .` を実行し、FPM/Nginx構文確認を含むビルドを確認。push・PR・デプロイは内容確認後にご自身で行う。

### デプロイ後の確認

- 起動ログ：Migration、キャッシュ生成、Nginx/FPM構文確認、Supervisorの両プロセスRUNNING。storageのPermission deniedがないこと。
- `/health` が204、`/up` が200、`/app.webmanifest` が200でJSONを返し、start_urlが `/pwa/handoff/…` になっていること。
- Home/ログイン/Guestの既存計画/共同計画の閲覧・編集、未来メモとAI共有OFF、フィードバックの投稿・公開・取り消し。
- iOSの新規PWAインストールとログイン引き継ぎ。既存PWAは更新バナーから更新してオフライン画面も確認。
- オフラインで開始・一時停止→接続復帰→終了。同期通信を一度失敗させても「同期を再試行」が使え、作業ログが1件だけになること。
- メモリ・CPU・応答時間を以前と比較。今回の変更だけで40人を処理できるという保証はしていません。

### 戻す場合

後続変更がないことを確認して `rollback/` の中身を上書きし、manifestで `base_sha256: null` の追加ファイルだけを取り除いてください。DB構造は変更していないため、DBの巻き戻しは不要です。PWAのシェルは通常のService Worker更新経由で戻します。
