# V40.6 Entitlement Foundation

## Purpose

V40.6 prepares Canovia for a future economy without introducing monetization UX yet.

The product direction is:

- core goal-achievement support remains meaningfully usable for free
- the same published Feature may be usable through different entitlement sources
- feature code must not know whether access came from Premium, Coin, Gift, Sponsor, or Free
- StoreKit / Coin / Gift / Sponsor implementation is deferred until the iOS monetization phase

The desired feature-side question is only:

> Can this actor use this Feature?

---

## Non-goals

V40.6 does **not** implement:

- StoreKit
- App Store purchases
- Premium subscription purchase
- Premium UI
- Coin balance
- Coin purchase
- Coin consumption
- Earn Coin
- Gift
- Sponsor records
- Sponsored Access UI
- Paywall
- pricing
- Coin earning rates
- Coin spending rates
- cash-out / conversion

There is no `users.is_premium` column and no billing migration.

---

## Responsibility boundaries

Three concepts remain separate.

### 1. Feature Flag

Question:

> Is this functionality published / visible at all?

Current location:

`config/features.php`

Examples:

- internal AI not ready
- beta feature hidden
- staged rollout

FeatureAccessService does **not** read Feature Flags.

### 2. Entitlement

Question:

> This Feature is published. May this actor use it?

Boundary:

`FeatureAccessService`

Examples of future access sources:

- Free
- Premium
- Coin
- Gift
- Sponsor

### 3. Ownership / collaboration authorization

Question:

> May this actor view/edit this specific Plan / Task?

Boundary:

`PlanOwnershipService`

Examples:

- Plan owner
- collaborative editor
- collaborative viewer
- Guest owner token

Entitlement never replaces ownership checks.

A user may be entitled to Project Artifact as a product Feature and still be unable to edit another user's Plan.

## Feature keys

Canonical enum:

`App\Enums\FeatureKey`

Initial stable keys:

- `ai_practice`
- `advanced_analytics`
- `question_pack`
- `project_artifact`
- `automatic_ai_execution`

The enum is the application-side identifier.

`config/entitlements.php` must contain the same keys.

The V40.6 regression test locks this mapping.

---

## Access sources

Canonical enum:

`App\Enums\EntitlementSource`

Values:

- `free`
- `premium`
- `coin`
- `gift`
- `sponsor`

Only Free has a resolver in V40.6.

The remaining values reserve stable semantics without deciding storage, pricing, duration, or grant rules prematurely.

---

## FeatureAccessService

Public boundary:

```php
$decision = $featureAccess->resolveAccess(
    $request->user(),
    FeatureKey::AiPractice,
    ['plan_id' => $plan->id, 'task_id' => $task->id],
);

$allowed = $featureAccess->canUse(
    $request->user(),
    FeatureKey::AiPractice,
);

$featureAccess->authorizeUse(
    $request->user(),
    FeatureKey::ProjectArtifact,
);
```

Feature code must not use:

```php
if ($user->is_premium) { ... }
if ($user->coin_balance >= 100) { ... }
if ($user->has_gift) { ... }
```

Those details belong behind entitlement resolvers.

---

## FeatureAccessDecision

`FeatureAccessDecision` returns:

- Feature
- allowed / denied
- access source
- reason
- optional internal metadata

Example today:

```
feature = ai_practice
allowed = true
source = free
reason = free_access
```

Possible future result:

```
feature = advanced_analytics
allowed = true
source = sponsor
reason = school_sponsorship
```

The consuming Feature should behave the same in both cases.

---

## Resolver pipeline

Contract:

`App\Contracts\EntitlementResolver`

Each resolver:

- declares its EntitlementSource
- declares priority
- returns an allow decision when that source grants access
- returns null when that source does not apply

Current pipeline:

```
FeatureAccessService
    ↓
FreeEntitlementResolver
    ↓
allow
```

Future example:

```
FeatureAccessService
    ↓
SponsoredEntitlementResolver
    ↓
GiftEntitlementResolver
    ↓
CoinUnlockEntitlementResolver
    ↓
PremiumEntitlementResolver
    ↓
FreeEntitlementResolver
```

The exact future order can be changed without touching feature code.

Resolvers are registered through Laravel's tagged container binding in `AppServiceProvider`.

---

## Current policy

`config/entitlements.php`

uses:

```php
'default_policy' => 'allow'
```

and explicitly marks every current Feature as:

```php
'free' => true
```

Therefore V40.6 changes no existing user's access.

When monetization begins, a Feature can stop receiving Free access by changing its policy and adding the required resolver(s).

Example conceptually:

```php
'advanced_analytics' => [
    'free' => false,
],
```

A Premium resolver could then grant the same Feature.

No Feature controller needs to know why.

---

## Context and scoped entitlements

`FeatureAccessService` accepts optional context.

Current calls may include:

- `plan_id`
- `task_id`
- `route_name`

V40.6's Free resolver ignores this context.

Future resolvers may use it for scoped access such as:

- Coin unlock for one Question Pack
- Gift access to one Feature for a limited period
- Sponsor access within a school program
- organization-specific Advanced Analytics

This keeps scope decisions out of Feature code without prematurely defining database tables.

## Current integrations

### AI Practice

All Study Practice routes use:

`feature.access:ai_practice`

Current result: allowed through Free.

### Question Pack

Question Pack is deliberately separate from AI Practice.

The Study Practice controller asks:

`canUse(actor, FeatureKey::QuestionPack)`

If Question Pack is unavailable in the future, the existing external-AI provider can be selected instead.

The Question Pack direct-prepare action independently requires Question Pack access.

Current result: allowed through Free, so provider behavior is unchanged.

### Project Artifact

All Project Artifact routes use:

`feature.access:project_artifact`

Plan Tool presentation also asks FeatureAccessService before recommending the Artifact Tool.

Current result: allowed through Free.

### Tool presentation

`PlanToolService` uses FeatureAccessService for Feature-backed tools.

Both:

- Plan detail
- Dashboard Guidance

pass the current authenticated actor when available.

Guest remains represented as `null` and receives current Free access.

## Route middleware

Reusable middleware:

`EnsureFeatureAccess`

Alias:

`feature.access`

Example:

```php
Route::middleware('feature.access:project_artifact')->group(...);
```

This makes endpoint enforcement use the same boundary as UI/tool availability.

The middleware does not implement a Paywall.

When access is denied today, it returns 403.

A monetization phase may replace that presentation behavior without changing FeatureAccessService semantics.

---

## StoreKit integration later

V40.6 intentionally does not model StoreKit receipts.

A future iOS architecture can be:

```
StoreKit / App Store Server API
        ↓
subscription entitlement storage / verification
        ↓
PremiumEntitlementResolver
        ↓
FeatureAccessService
        ↓
existing Feature
```

Feature controllers do not need `StoreKit` conditionals.

The backend can remain the source of truth for server-backed Features.

---

## Coin later

Coin is expected to be a non-cash-out Canovia internal point at least initially.

V40.6 does not define:

- balance column/table
- Coin price
- purchase package
- spending amount
- expiration
- Earn Coin rate

A future Coin resolver can inspect a durable unlock/grant record and return:

```
source = coin
```

The actual transaction ledger should be designed only after product behavior and App Store requirements are concrete.

---

## Gift and Sponsor later

Gift and Sponsor are also modeled as future access sources, not current database models.

Possible future resolver responsibilities:

### Gift

- recipient
- Feature
- scope
- granted_at / expires_at
- gift status

### Sponsor

- organization / program
- eligible user
- Feature set
- start/end period

Neither requires Feature code changes.

---

## Observability

V40.6 does not log every access check.

Logging every render-time `canUse()` call would create noise before there is a business need.

Instead:

`FeatureAccessDecision::auditMetadata()`

provides a safe future event shape:

- `feature_key`
- `allowed`
- `access_source`
- `access_reason`

The single FeatureAccessService boundary is the future hook point for BehaviorEvent or dedicated entitlement analytics.

Receipt payloads, Coin ledger details, or private sponsor data should never be copied into BehaviorEvent metadata.

---

## Why no entitlement database table yet

The future grant models are not equivalent:

- Premium is subscription state
- Coin may unlock consumable or durable access
- Gift has sender/recipient semantics
- Sponsor may be organization/program scoped

Forcing all of these into one generic entitlement table before product rules exist risks creating an abstraction that does not fit any of them well.

V40.6 stabilizes the interface first.

Storage is deferred until the corresponding source is implemented.
