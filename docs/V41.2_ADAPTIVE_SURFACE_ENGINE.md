# V41.2 Adaptive Surface Engine

## Goal

Canoviaの機能が増えても、ユーザーに「機能一覧から必要なものを探す」ことを要求しない。

V41.2ではPlan Hubを固定カードの集合から、**Category Profile × Situation × Surface Module**で組み立てる構造へ変更する。

```text
Plan
  ↓
Category Profile
  ↓
Situation Resolver
  ↓
Surface Engine
  ↓
Plan Hub / Roadmap
```

現在はrule-based。将来AIを導入しても同じSurface IDを使い、UI実装そのものは固定・安全なまま優先順位だけを変更できる。

## Category Profile

`PlanCategoryProfileService` はPlan.categoryを次のprofileへ正規化する。

- study
- career
- development
- creative
- general

profileは現在以下を持つ。

- profile key / label
- preferred roadmap renderer
- roadmap title / description
- surface tone

### Current renderer policy

V41.2時点ではRoadmap本体のrendererは安全な `task_flow` を維持する。

Category Profileは将来の推奨rendererを返す。

- study -> `study_map`
- career -> `pipeline`
- development -> `delivery_flow`
- creative -> `milestone`
- general -> `task_flow`

Roadmap画面はprofileに応じてタイトル・説明を切り替え、DOMへpreferred / active rendererを明示する。
将来rendererを追加してもCategory Profile契約を変更せず接続できる。

## Situation Resolver

`PlanSituationResolver` は、Planのcategoryだけではなく現在状況を解決する。

共通Signal:

- active / done Task count
- Current Task
- deadline days / deadline soon / overdue
- recent Evidence
- Artifact / Resource
- AI Practice availability

カテゴリ別Signal:

### Career

既存Taskをtitle / description / next_actionから次へ分類する。

- discovery: 企業・職種探し
- application: 応募・書類
- interview: 面接・選考
- offer: 内定・条件確認
- other

専用のApplication tableがない現在でも、既存TaskからCareer Pipelineを構成できる。

Interview Taskがactiveなら `career_has_interview=true` となり、Interview Focus Surfaceが現れる。
全Interview Taskが完了するとそのSurfaceは消える。

### Study

直近の `study_practice_assessed` Evidenceから、

- score
- weaknesses
- next action

をSituationとして返す。

### Development / Creative

Artifact数と `artifact_state_observed` Evidenceを使い、成果物を前に出す必要があるか判断する。

## Surface Modules

V41.2で登録するmodule:

### Generic

- current_task
- recent_evidence
- task_list
- plan_tools
- recent_activity

### Career

- career_pipeline
- career_interview_focus

### Study

- study_focus

### Development / Creative

- delivery_focus

各moduleは以下を持つ。

```text
id
view
priority
visibility
reason
payload
```

Dashboard Bladeはmoduleのpriority順でregistered viewをincludeする。
個別カードの並びをDashboard本体へ直書きしない。

## Example: Career

### Before interview exists

```text
Current Task
Career Pipeline
Task List
Plan Tools
Recent Activity
```

### While interview Task exists

```text
Interview Focus
Current Task
Career Pipeline
Recent Evidence
Task List
Plan Tools
Recent Activity
```

### After interview Tasks are completed

Interview FocusはSurface Engineから外れる。

## AI-ready policy boundary

AIにUI HTML / Blade pathを生成させない。

`PlanSurfaceEngine::policyContext()` はAI向けに次だけを出せる。

- Plan descriptor
- Category Profile
- sanitized Situation
- registered module ids
- default priority / visibility / reason

将来AIが返せる想定output:

```json
{
  "ordered_module_ids": ["career_interview_focus", "current_task", "career_pipeline"],
  "hidden_module_ids": ["recent_activity"]
}
```

`applyDecision()` はregistered moduleだけを受け付ける。

- unknown module idは無視
- arbitrary view / HTMLは受け付けない
- current_task / plan_toolsはprotectedで非表示不可

この契約により、AI導入後も「何を前面に出すか」はAI化できるが、「何を描画できるか」はCanovia側が制御する。

## Career category

Plan作成/編集に `就活・キャリア` を追加する。

Future Memoの `就職・将来 / career` からPlan作成へ進む場合も同カテゴリへ引き継ぐ。

## Current limitations

Career Pipelineは現在**Task由来**であり、応募企業ごとの専用データモデルではない。

そのためV41.2では、

- 企業名
- 応募日
- 選考stage
- 面接日時
- 結果
- offer条件

を独立したApplication entityとしては持たない。

今後Career機能を深める場合、`CareerApplication`等を追加し、
Career Pipeline Surfaceのdata providerだけを差し替えればよい。
Surface Engine / Dashboard契約は維持できる。
