# V41.3 Career Capture / Application / Interview Review

## Goal

就活管理のためにユーザーへ入力作業を要求しない。

理想は、

```text
ユーザー
  求人を見る
  応募する
  面接を受ける
  必要ならスクショを投げる

Canovia
  情報をCapture
  応募先と照合
  選考Stageを把握
  面接前後のSurfaceを切替
  振り返りを次の面接へ接続
```

V41.3ではAI・Gmail・Calendar連携そのものより先に、その情報を受け取れる共通データ境界を実装する。

## Career Capture

`CareerCapture` は入力経路と応募管理本体を分離するInbox。

source_type:

- screenshot
- url
- email
- calendar
- manual

V41.3のユーザーUIでは screenshot / url を利用可能。
email / calendar は将来Connectorから同じ `CareerCaptureService` へ投入する予約source。

fields:

- plan_id
- career_application_id
- actor
- source_type
- status
- source_url
- screenshot metadata
- raw_text
- extracted_data
- confidence
- captured_at

### Screenshot storage

Renderの現在構成に永続ディスクを前提にしないため、V41.3のスクリーンショット本体は `career_capture_payloads` へ非公開Payloadとして保存する。

- max 3MB
- production PHP upload limit: 4MB / POST limit: 6MB
- JPEG / PNG / WebP
- Base64をMEDIUMTEXTへ保存
- Capture一覧ではPayload本体をloadしない
- 専用routeでPlan閲覧権限を確認してから返す
- public URLは生成しない

`screenshot_path` は将来S3等のobject storageへ移行するための境界として残す。

画像量が増える段階ではDB Payloadからobject storageへ移行する。

## Career Application

`CareerApplication` は実際の応募先・候補を表す。

stages:

```text
candidate
preparing
applied
screening
interview
final_interview
offer
closed
```

主なfields:

- company_name
- company_website
- role_title
- stage
- status
- applied_at
- next_event_at
- result
- metadata

V41.3では自動抽出AIがないため、Applicationが未知のCaptureはpendingのまま保存できる。

手動追加はfallbackとして折りたたみUIに置き、通常導線にはしない。

## Career Pipeline

V41.2ではTask名からPipelineを推定していた。

V41.3ではCareerApplicationが1件以上あれば実データを優先する。

```text
候補・応募準備
応募・書類
面接・選考
内定・条件確認
終了
```

Applicationがまだ無いPlanではV41.2のTask inferenceへfallbackする。

これにより導入途中でも既存Planを壊さない。

## Selection Event

`CareerSelectionEvent` は面接等の選考Eventを表す。

V41.3 UIではInterview Eventを作成できる。

fields:

- application
- optional Task
- source Capture
- type
- stage
- status
- scheduled_at
- completed_at
- result
- notes

面接TaskがPlan内に1件だけ明確に存在する場合、Event作成時に自動でTaskへ接続する。

## Surface lifecycle

Career SurfaceはEvent状態で切り替わる。

```text
future scheduled interview
  -> career_interview_prep

interview time elapsed
+ no completed Review
  -> career_interview_review
  ※ 時刻経過だけでは「面接実施済み」と確定しない。
     実施されなかった予定はCareer Workspaceからcancelできる。

Review completed
  -> career_result_waiting

Result recorded
  -> result waiting disappears
     application stage/status changes
```

Current TaskはV41.2同様、共通anchorとして最上位に残す。

## Interview Review

Interview Reviewの目的は合否予想ではない。

```text
面接
  -> 自分が観測したこと
  -> 良かったこと
  -> 難しかったこと
  -> 答え直したいこと
  -> 企業への印象
  -> 次回の改善点
```

を結果が出る前に保存し、次の面接へ持ち越す。

### State-aware questions

質問はViewへ固定文字列として埋め込まず `InterviewReviewQuestionService` から供給する。

基本質問:

- best_moment
- asked_questions（実際に聞かれた質問を、覚えている範囲で残す）
- difficult_moment
- redo_answer
- company_impression
- next_focus

過去のcompleted Reviewに `next_focus` がある場合、

```text
前回「○○」を意識すると振り返っていました。
今回は実践できましたか？
```

を先頭へ追加する。

final interviewでは意思決定前の確認事項も追加する。

つまりAI導入前でも `Situation -> Question` の最小ループを成立させる。

### AI upgrade path

`InterviewReviewAnswer` は、

- question_key
- prompt
- answer
- source
- sort_order

を保存する。

今はsourceが rule / rule_context / rule_stage。

将来は同じschemaで、

```text
Plan context
+ Company
+ Application stage
+ Past Interview Reviews
+ Evidence
+ User traits
  ↓
AI Question Policy
  ↓
question_key / prompt / source=ai
```

へ差し替えられる。

Review UIや保存schemaは変更不要。

実際に聞かれた質問も `asked_questions` としてReview / Evidenceへ残す。将来Interview Practiceを実装する場合、この履歴を企業・選考段階・本人の弱点と組み合わせて、現実の面接に近い練習質問へ再利用できる。

## Evidence

Interview Reviewがcompletedになり、Selection EventがTaskへ紐づいている場合:

```text
source = native
type = interview_review_completed
confidence = 1.0
```

を作成する。

Selection Resultをユーザーが確定した場合:

```text
source = native
type = interview_result_recorded
confidence = 1.0
```

を作成する。

どちらも「事実が記録された確度」であり、Task progressを自動増加させない。

## Result lifecycle

Interview Review完了後はEventを `result_waiting` にする。

結果:

- passed
- rejected
- offer
- withdrawn

を記録するとEventはcompletedになる。

rejected / withdrawn:
- Application -> closed

offer:
- Application -> offer

passed:
- Applicationはactiveを維持し、次Eventを待つ

## Connector path

将来の自動取得はApplicationへ直接書き込ませず、まずCaptureへ入れる。

```text
Gmail
Calendar
Screenshot AI
Share Sheet / URL
Browser extension
  ↓
CareerCaptureService
  ↓
CareerCapture
  ↓
Extractor / Matcher
  ↓
CareerApplication
  ↓
CareerSelectionEvent
  ↓
Surface Engine
```

この境界により、取得方法が増えてもApplication/Surface側を作り直さない。

## Not in V41.3

- screenshot OCR / vision extraction
- Gmail Connector
- Calendar Connector
- Company情報のWeb自動取得
- Application重複のAI照合
- AI生成Interview Review questions
- Company Fit分析
- 職業推薦
- Interview Practice native tool
- 自動的な選考結果推定

これらはCapture / Application / Reviewの既存境界へ追加する。
