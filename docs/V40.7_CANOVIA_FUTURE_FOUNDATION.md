# V40.7 Canovia Future Foundation

## Purpose

V40.7 turns Feedback into a lower-friction product discovery loop while preserving the existing free-form channel.

The release also introduces the minimum Feature Flag boundary needed to keep runtime publication separate from Entitlement.

## Implemented

### Feature Flag boundary

New service:

`App\Services\FeatureFlagService`

The service answers only:

> Is this Feature currently enabled for this runtime context?

It does not call `FeatureAccessService` and does not inspect Premium/Coin/Gift/Sponsor state.

Current supported metadata:

- enabled
- environment
- platform
- minimum app version

Persistence remains config-based in V40.7. DB-backed remote flags and Admin controls are deferred.

### Canovia Future

New GET route:

`/feedback`

The existing global Feedback entry now opens this page instead of immediately opening the free-form dialog.

The page presents published Roadmap candidates and lets an actor add/remove one Support per candidate.

The existing POST `/feedback` free-form Feedback endpoint remains unchanged and the existing dialog is still available from "その他のフィードバック".

### Roadmap data model

`roadmap_features`

- stable `feature_key`
- title / description
- threshold
- status
- sort_order
- published flag
- voting enabled flag
- released_at

`roadmap_votes`

- roadmap feature
- optional user
- optional actor token
- stable `voter_key`

Unique constraint:

`roadmap_feature_id + voter_key`

Authenticated actors use `user:{id}`. Guests use the existing BehaviorIdentity actor token.

### Initial candidates

The migration seeds the first discovery set:

- other people's progress
- same-goal peers
- Achievement sharing
- Cheer
- Gift
- more automatic AI plan adjustment

These are Roadmap ideas, not implemented product Features.

## Status lifecycle

- voting
- considering
- planned
- in_development
- ready
- rolling_out
- released

A status does not automatically enable a runtime Feature Flag.

## Threshold semantics

The UI intentionally says that the threshold is a signal for Roadmap consideration, not a delivery promise.

`500 Support` means approximately:

> enough demand to enter formal product consideration / Roadmap discussion

Canovia still controls final priority.

## Why Roadmap feature keys are not automatically Entitlement FeatureKey cases

An idea under discovery is not yet necessarily a runtime Feature.

For example, `social.cheer` can exist in Roadmap Voting before any executable Cheer Feature exists. Adding every idea to `FeatureKey` would incorrectly imply that it already has an entitlement/runtime contract.

When an idea becomes an implemented Feature, the implementation phase decides whether it needs a canonical `FeatureKey` and entitlement policy.

## Feedback compatibility

No existing Feedback row or Admin Feedback workflow is removed.

Free-form Feedback still supports:

- usability
- bug
- request
- positive
- rating
- message
- Plan / Task / Page context
- release-note publication from Admin

## Not implemented

- Roadmap Admin editor
- automatic status promotion at threshold
- notifications when a supported Feature changes status
- Release Note foreign key from Roadmap Feature
- remote DB-backed Feature Flags
- percentage rollout
- StoreKit / Premium purchase
- Coin / Earn Coin
- Gift transaction model
- Sponsored Access
- Social Feed / Follow / Cheer runtime Features

## App Store boundary

Future remote release is intended only for functionality already included in a reviewed binary and appropriately disclosed to App Review.

The planned flow is:

```text
implement
→ review/disclose
→ distribute binary
→ enable gradually through Feature Flag
```

It is not a mechanism for shipping a large undisclosed hidden product and enabling it after review.
